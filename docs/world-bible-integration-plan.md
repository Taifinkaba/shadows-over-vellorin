# World Bible integration plan — chunk 1

**PROPOSED architecture only.** No entities, schemas, registries or campaign events are implemented by this document. Read the [evidence audit](world-bible-integration-audit.md) before adopting any expansion.

## One owner per fact

Reuse `entities/<type>/<id>.md` and `index.json` schema2. Keep existing supported types: characters, creatures, items, locations, quests, factions, rules and mechanics. New records, when separately approved, need unique stable IDs, existing normalized `source_refs`, frontmatter status/visibility matching the index, and provenance that distinguishes approved design, actual events, testimony and uncertainty. Audit labels such as PROPOSED are review classifications, not new allowed frontmatter statuses.

`state/checkpoint.json` remains the current snapshot. `state/finance-ledger.json` remains the detailed money authority, routed through `party-finances`; existing structured `checkpoint_values` owners remain authoritative. Entity prose and checkpoint projections must agree when canon is updated. `archive/` preserves evidence, never a rival current dataset. `changes/chronicles/` records sourced rulings/events; `state/open-verifications.md` carries unresolved provenance. Directories link owners and summarize dated facts rather than copying mutable balances, NPC positions or quest conclusions.

## Expansion intake contract

Before implementation, capture the exact supplied 1.0–2.2 versions as immutable evidence with version/source provenance. Do not assume the existing v1.0 archive contains later expansions. Build a review crosswalk with: proposed claim, expansion version/section, existing ID/path, existing supporting or conflicting source, classification, proposed owner, visibility/discovery boundary, player decision and implementation PR. Prefer existing IDs; aliases are not identity proof. Keep this crosswalk in documentation until approval, so proposals cannot be mistaken for active entities.

For prospective institutions, identify powers, territorial scope and relationship to existing magistrates/watch/guilds before defining people. For dungeon entries, match names/aliases and exploration history before assigning a new ID. For quests, compare every proposed answer with played evidence and pending mysteries. For laws and price tables, preserve design status and distinguish current enacted law/quoted price from reference bands. No unsupported new kingdom, official or quest outcome is created in chunk1.

## Implementation sequence and acceptance gates

1. **Source intake and player decisions — REQUIRES APPROVAL.** Obtain complete versioned expansions; review the crosswalk, Concord/jurisdiction proposals, identity ambiguities, secrets and publication policy. Keep unsupplied facts UNKNOWN. No visibility change is implied.
2. **Checkpoint reconciliation — REQUIRES APPROVAL in a separate PR.** Preserve the existing Day156 snapshot/structured owners/ledger as historical fixtures before any approved Day181 adoption. Record the supplied later checkpoint as a supplied endpoint, not fabricated play. Resolve or explicitly retain missing status, room, mask state, account allocation and −26gp/+22MP provenance. Update checkpoint, affected owners/prose, ledger, chronicle, handoff and verification queue together only when authorized. Do not create balancing transactions or a fictional rest; do not infer the26gp came from Blackscale private funds.
3. **Directories over existing IDs — PROPOSED.** Add location/route, settlement/business and dungeon routing entries from existing sources first. Distinguish observed, historical and approved design. Retain unknown site equivalences. Check every link and source; do not require a global entity-type migration.
4. **Institutions and contracts — PROPOSED / REQUIRES APPROVAL.** Integrate approved Concord and justice design into existing factions/rules/characters and custody routing, without replacing existing institutions, transferring prisoners, canceling unrelated notices or granting immunity. Promote archived secondary organizations only with classification and evidence review.
5. **Economy and autonomous activity — PROPOSED.** Extend existing financial/assignment records only for supplied details; document schema changes before code. Preserve317gp unpaid expansion, noncash exclusions and existing expenses. Actual future work, wages, income and events require supported records or explicit player rulings.
6. **Quest and GM review — REQUIRES APPROVAL for changed answers.** Check mysteries, testimony, pending reviews and knowledge provenance before adopting prospective lore. Keep secret content out of player-facing directories and PR summaries. No offscreen resolution.
7. **World-status projection — PROPOSED.** Generate a dated, read-only view from the established owners after ownership and visibility are reliable. Test missing-data rendering, source links and secret filtering before using a player-facing mode.

Each stage is a small reviewable PR on an allowed branch with source citations and changelog. Implementation approval does not authorize advancing play, changing resources, transferring custody or merging. User approval remains required for merge.
